# Designer / Product Site Brief

Дата: 2026-06-30.

Этот бриф можно дать AI-агенту-дизайнеру или агенту, который будет готовить продуктовую упаковку, страницу проекта, лендинг, README для внешней аудитории или презентационное описание Диктум.

Главная цель: дать агенту достаточно контекста, но не заставлять его читать весь репозиторий, внутреннюю историю разработки, research notes, приватные outputs и agent-журналы.

## Коротко о продукте

Диктум - локальный private-first инструмент для macOS, который превращает длинные диктофонные записи в текстовые протоколы с разделением по спикерам.

Продукт нужен людям, которые часто работают с записями интервью, консультаций, обучений, вебинаров, семинаров, рабочих встреч и голосовых заметок. Ценность: не просто "получить текст", а получить пригодный для дальнейшей работы протокол обсуждения: с таймкодами, репликами разных людей, именами спикеров и экспортом в удобные форматы.

Текущий baseline:

- локальный Mac-продукт, не SaaS;
- приватность по умолчанию;
- загрузка аудио через локальный web UI или папку `Inbox/`;
- ASR: `GigaSTT / GigaAM v3 RNNT`;
- speaker diarization: pyannote;
- длинные записи обрабатываются через chunking;
- текущая trial-упаковка - zip с double-click launchers;
- self-host, публичный GitHub, лендинг и native macOS wrapper пока не являются готовым продуктом.

## Что дизайнеру прочитать

Читать в этом порядке. Не открывать весь проект целиком.

### 1. Авторская идея

Файл: `Описание идеи проекта от автора.docx`

Зачем читать:

- это лучший источник живой формулировки проблемы;
- там описаны реальные сценарии автора: интервью, обучения, многочасовые записи, подготовка текстов для AI-агентов;
- там есть важный образ целевого пользователя: не разработчик, а обычный Mac-пользователь, например консультант или методолог.

Как использовать:

- извлечь человеческий язык проблемы;
- НЕ публиковать сам файл;
- НЕ включать личные формулировки дословно без редактуры;
- превратить в короткий product story.

## Что НЕ читать без отдельной причины

Чтобы не тратить токены и не засорять вывод внутренней историей:

- `.agents/task-board.md` полностью, кроме этого брифа;
- `.agents/product-backlog.md` полностью, если задача не про roadmap;
- `docs/asr-*`, `docs/local-models.md`, `docs/external-projects.md`, `docs/handy-gigaam-e2e-runtime.md`;
- `docs/security-*`, если задача не про security page;
- `docs/ux/voice-recognizer-prototype.html`, если не делается UI redesign;

- `.env`, `.venv/`, `.models/`, `.cache/`, `.local-quality/`, `outputs/`, `Inbox/`, `logs/`, `tools/bin/`;
- старые `.dist/` сборки, кроме последней явно указанной.

## Позиционирование

Возможная краткая формула:

> Local-first transcription workspace for long Russian voice recordings: upload recordings, transcribe them locally, separate speakers, name voices and export clean protocols for further work.

На русском:

> Локальный рабочий инструмент для длинных диктофонных записей: распознает речь, разделяет реплики по спикерам, помогает подписать голоса и выгрузить чистый протокол обсуждения.

## Целевая аудитория

Основные пользователи:

- консультанты;
- методологи образовательных программ;
- исследователи и интервьюеры;
- коучи/психологи/эксперты, работающие с записями сессий;
- организаторы обучений и вебинаров;
- люди, которые кормят текстами AI-агентов и хотят получить качественный протокол из аудио.

Важно: это не "приложение для разработчиков". Первый образ качества - человек на Mac, который может распаковать zip и запускать `.command` файлы без Terminal.

## Главные продуктовые обещания

Можно использовать на лендинге/упаковке, если не обещать больше текущей реализации:

- локально и приватно на Mac;
- для длинных записей, включая часы аудио;
- для русского языка;
- разделение по спикерам;
- переименование спикеров после распознавания;
- пакетная обработка и очередь;
- результаты открываются кликом;
- экспорт в Markdown/TXT и другие рабочие форматы;
- нет обязательной подписки и облачной отправки аудио по умолчанию.

Осторожные формулировки:

- не обещать идеальное качество ASR/diarization;
- не обещать нативное `.app`, notarization или App Store;
- не обещать публичный self-host/Docker release прямо сейчас;
- не обещать все альтернативные ASR-движки в UI;
- не обещать автоматическое узнавание постоянных людей по голосу.

## Что нужно получить от дизайнера

Минимальный ожидаемый результат:

1. Product positioning: название, tagline, 1-2 абзаца описания.
2. Landing/site structure:
   - hero;
   - problem;
   - how it works;
   - privacy/local-first;
   - user scenarios;
   - current trial/install path;
   - feedback/early access call-to-action.
3. External README / product page copy, без внутренней кухни проекта.
4. Trial-pack wording suggestions:
   - улучшить `START_HERE.txt`;
   - улучшить `FEEDBACK_TEMPLATE.txt`;
   - предложить имена файлов/кнопок, понятные обычному пользователю.
5. Visual direction:
   - спокойный рабочий инструмент;
   - не SaaS-маркетинг с лишней декоративностью;
   - интерфейс должен выглядеть как инструмент для повторяемой работы с файлами и результатами.

Если агент умеет делать дизайн-макеты:

- предложить landing mockup;
- предложить screenshot/storyboard текущего local workflow;
- не менять приложение без отдельной задачи.
