# UX Acceptance Scenarios

Дата: 2026-06-26.
Автор: Claude (UX/product track).

Назначение: превратить пользовательские сценарии (`docs/user-scenarios.md`) и критерии приёмки из `docs/agent-redesign-proposal.md` в проверяемые сценарии «Given / When / Then» с ручными шагами. Это приёмочный слой для implementation- и review-агентов: реализовал поведение → прогнал сценарий → отметил pass/fail. Каждый сценарий привязан к находкам аудита (`docs/ux-audit.md`, F1–F14) и к пунктам `.agents/review-checklist.md`.

Эталон целевого поведения: `docs/ux/voice-recognizer-prototype.html`.

## Как прогонять

Поднять тестовый сервер на нестандартном порту и проверять в браузере (правило из `CLAUDE.md` / `AGENTS.md`):

```bash
VOICE_RECOGNIZER_PORT=8782 VOICE_RECOGNIZER_OPEN_BROWSER=0 VOICE_RECOGNIZER_PAUSE_ON_EXIT=0 app/scripts/start_server.sh
# открыть http://127.0.0.1:8782 , пройти сценарии, проверить console на ошибки
VOICE_RECOGNIZER_PORTS=8782 VOICE_RECOGNIZER_PAUSE_ON_EXIT=0 app/scripts/stop_server.sh
```

Тестовые данные: положить в `Inbox/` короткий (≤2 мин) и длинный (≥90 мин, можно фрагментный прогон) аудиофайл. Не коммитить тестовые аудио и выходные артефакты.

Статус каждого пункта: ☐ не проверено · ✅ pass · ❌ fail.

## S1 — Один файл целиком

Покрывает: `user-scenarios.md` §1; proposal сценарий A; review-checklist «UI».

Given в `Inbox/` есть аудиофайл, сервер запущен, очередь пуста.

When пользователь:
1. выбирает файл в списке Inbox (один клик);
2. оставляет режим «Один файл» и пресет по умолчанию;
3. нажимает «Запустить выбранный».

Then:
- ☐ выбранный файл подсвечен и остаётся выбранным после запуска (review-checklist: «keep uploaded file selected»);
- ☐ задача появляется в очереди со статусом **Ожидает/Выполняется** (русским, F5);
- ☐ строка Inbox показывает длительность и формат, а не только размер (F7);
- ☐ если файл уже обрабатывался, в строке Inbox виден бейдж «обработан · готово →» с переходом к результату (F16);
- ☐ основной путь «выбрал → запустил» не требует ручного ввода секунд или знания CLI;
- ☐ страница не перезагружается; console без ошибок.

## S2 — Тест-фрагмент

Покрывает: `user-scenarios.md` §2; proposal сценарий B / §3.3; audit F6.

Given выбран файл.

When пользователь переключает режим на «Тест-фрагмент» и нажимает пресет «2:00».

Then:
- ☐ «Тест-фрагмент» — отдельный режим, а не два пустых числовых поля (F6);
- ☐ доступны быстрые пресеты `0:30 / 2:00 / 5:00` и ввод времени в `мм:сс`;
- ☐ показан читаемый readout диапазона (например `0:00–2:00`);
- ☐ `мм:сс` корректно конвертируется в секунды для API;
- ☐ при длительности больше длины файла — понятная валидация рядом с полем, запуск заблокирован (proposal «Настройки и валидация»);
- ☐ повторный тест с другими настройками не стирает результат предыдущего.

## S3 — Пакетная обработка Inbox

Покрывает: `user-scenarios.md` §3; proposal сценарий C; audit F11; review-checklist «Batch mode does not start uncontrolled parallel heavy jobs».

Given в `Inbox/` несколько файлов.

When пользователь переключается в режим «Пакет», снимает галочку с одного файла и ставит пакет в очередь.

Then:
- ☐ в режиме «Пакет» у файлов появляются чекбоксы; можно исключить файл (F11);
- ☐ видна сводка пакета: всего / выполняется / ожидает / готово / ошибок;
- ☐ задачи запускаются **последовательно** (не параллельная тяжёлая нагрузка на Mac);
- ☐ режим «Пакет» визуально отличается от одиночного запуска;
- ☐ можно открыть готовый результат, пока остальные обрабатываются.

## S4 — Разметка и имена спикеров

Покрывает: `user-scenarios.md` §4; proposal сценарий D / §3.7; audit **F2**; review-checklist «Polling does not wipe user edits in speaker name fields», «Audio samples play through and support range requests».

Given есть завершённая задача (**Готово**) со спикерами.

When пользователь открывает вкладку «Спикеры», проигрывает sample, печатает имя в поле спикера и **держит фокус в поле дольше 2 секунд** (один цикл polling), затем нажимает «Применить имена».

Then:
- ☐ **введённый текст не стирается во время polling** — критическая проверка F2 (печатать ≥5 c, наблюдать минимум два цикла обновления очереди);
- ☐ фокус и позиция каретки сохраняются после фонового обновления;
- ☐ sample проигрывается целиком (range-запросы, review-checklist);
- ☐ после «Применить имена» виден короткий статус **Применяю имена / перерендер экспорта**, а не полный повтор;
- ☐ ASR и диаризация **не** запускаются повторно; ссылки на экспорт обновляются;
- ☐ у спикера видно: цвет, число реплик, первое появление.

Регрессионный тест F2 (минимум):

```text
1. done-задача → вкладка «Спикеры».
2. Кликнуть в поле «Имя спикера 1», печатать «Андрей Петрович» по букве.
3. Не убирая фокус, продержать ~6 c (≥2 цикла обновления).
Ожидание: в поле «Андрей Петрович» целиком, каретка на месте, фокус не потерян.
```

## S5 — Длинная задача: этапы и elapsed

Покрывает: proposal §3.4 / §4 «Длинные задачи»; audit **F3**; task-board «Long task UX».

Given запущен длинный файл (или фрагментный прогон, эмулирующий длительность).

When пользователь смотрит на активную задачу и обновляет страницу в процессе.

Then:
- ☐ активная задача показывает **текущий этап** (Аудио → ASR → Диаризация → Склейка → Экспорт), а не общий «running» (F3);
- ☐ виден **elapsed** и время старта;
- ☐ виден последний значимый лог-heartbeat (задача «жива»);
- ☐ при отсутствии точного процента показан indeterminate-прогресс по этапам, без фальшивого процента;
- ☐ полный лог доступен, но свёрнут и не перетягивает фокус/скролл (F9);
- ☐ refresh страницы не ломает отображение текущей in-memory задачи (review-checklist).

## S6 — Диагностика ошибки и восстановление

Покрывает: proposal сценарий E / §4 «Ошибки»; audit **F4**; AGENTS.md DoD «путь не обрывается без next step».

Given задача падает по типовой причине (нет `HF_TOKEN`; нет доступа к pyannote; ошибка MPS; источник исчез; порт занят).

When пользователь открывает упавшую задачу.

Then для каждой типовой ошибки:
- ☐ показан **человеческий диагноз**, а не только traceback (F4);
- ☐ предложено конкретное действие: открыть `docs/setup-secrets.md`, повторить на CPU, принять условия модели, обновить Inbox;
- ☐ ошибка помечена `role="alert"` и объявляется скринридером (F10);
- ☐ форма запуска и выбранные настройки **не сбрасываются**; можно повторить с теми же настройками;
- ☐ сырой лог доступен вторым слоем, не первым;
- ☐ при недоступном сервере UI показывает локальную причину и следующий шаг, а не `TypeError: Failed to fetch` (F4).

Матрица типовых ошибок — см. таблицу в `agent-redesign-proposal.md` §4.

## S7 — Экспорт и проверка результата

Покрывает: `user-scenarios.md` §6; proposal §2 (вкладки) / §3.9; audit F8.

Given задача **Готово**.

When пользователь открывает результат.

Then:
- ☐ результат разложен по вкладкам **Обзор / Текст / Спикеры / Файлы** (proposal §2);
- ☐ во вкладке «Текст» — превью расшифровки с цветами спикеров, переключателем таймкодов, ширина строки ~65–75 символов (audit F-text);
- ☐ экспорты **сгруппированы**: Для чтения / Для редактуры / Для документов / Диагностика, с пояснениями (F8);
- ☐ виден `output folder` относительно корня проекта;
- ☐ при отсутствии samples/manifest — нейтральный empty state, не пустой блок;
- ☐ результаты открываются кликом из UI (review-checklist).

## S8 — Доступность и клавиатура

Покрывает: audit **F1**, F10, F13, F14; proposal «Визуальная и адаптивная приёмка».

Given любой экран.

When пользователь работает только с клавиатуры и/или со скринридером.

Then:
- ☐ у **всех** интерактивных элементов (кнопки, сегменты, строки Inbox/очереди, chip'ы) виден focus-ring (F1, WCAG 2.4.7);
- ☐ Tab-порядок совпадает с визуальным; все действия достижимы с клавиатуры;
- ☐ async-обновления (загрузка, постановка в очередь, готово, ошибка) объявляются через `aria-live`/`role=alert` (F10);
- ☐ статус различим не только цветом, но и текстом/иконкой (F13);
- ☐ контраст основного и приглушённого текста ≥ 4.5:1; `--soft` не используется для активного текста (F13);
- ☐ переходы 150–300 мс; при `prefers-reduced-motion: reduce` анимации отключаются (F14);
- ☐ нет горизонтального скролла на 1280 / 1024 / 768 / 375 px; зоны складываются в один поток на узком экране.

## S9 — Приватность и доверие

Покрывает: proposal §3.10 / «Приватность и доверие»; product-requirements «Модель приватности».

Then:
- ☐ в верхней панели постоянно виден локальный режим: `127.0.0.1` и «файлы не уходят в облако»;
- ☐ для локальных backend'ов нет формулировок, подразумевающих отправку в облако;
- ☐ если выбран внешний API-движок — рядом до запуска появляется явный privacy-warning.

## S10 — Повторное открытие результатов после рестарта

Покрывает: идею «уже обработан → готово → открыть»; audit **F15, F16**; proposal §4 «Очередь в памяти»; product-requirements (file-based storage).

Given накануне обработаны несколько файлов (в `outputs/` есть манифесты), сервер с тех пор перезапускался — in-memory очередь пуста.

When пользователь открывает UI и переключается на вид «Готовые» (или кликает «обработан · готово →» у файла в Inbox).

Then:
- ☐ вид «Готовые» показывает результаты, собранные с диска из `outputs/` (скан `*.manifest.json`), а не из in-memory очереди (F15);
- ☐ результаты видны после рестарта, включая те, для которых нет живой задачи в текущей сессии;
- ☐ у уже обработанного файла Inbox виден бейдж «обработан · готово →» с переходом к результату (F16);
- ☐ клик по результату открывает тот же блок (Обзор/Текст/Спикеры/Файлы) и позволяет назначить имена без повторного ASR;
- ☐ полный результат и тест-фрагмент того же файла различимы (full vs фрагмент);
- ☐ изменённый после обработки файл помечается «запись изменилась» (если включена проверка size/mtime) — желательное;
- ☐ результат с отсутствующими экспортами/манифестом показывает «частично», а не падает.

Backend-зависимость: `GET /api/results` (скан `outputs/`), поля `processed`/`results` в inbox payload, отрисовка результата из манифеста, при необходимости — обогащение манифеста. Контракт — в `.agents/handoff-ux-redesign.md` (раздел «Data contract»).
