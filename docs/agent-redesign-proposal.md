# Agent Redesign Proposal

Дата: 2026-06-26.

Документ описывает альтернативное UX-решение для локального web-интерфейса Диктум. Предложение опирается на текущую модель продукта: приватная обработка диктофонных записей, длинные файлы без лимитов за счет пайплайна и чанкинга, сменные ASR/diarization backend'ы, разметка спикеров и экспорт в рабочие текстовые форматы.

## 1. Ключевые пользовательские сценарии

### Сценарий A. Быстро получить текст из одного файла

Цель пользователя: выбрать запись из `Inbox`, запустить обработку с рекомендуемыми настройками и открыть готовый чистый текст.

Основной путь:

1. Пользователь видит список файлов в `Inbox` с длительностью, размером, форматом и признаком "новый / уже обработан".
2. Выбирает один файл.
3. Оставляет пресет `Максимальное качество, локально`.
4. Проверяет краткую строку настроек: ASR, diarization, устройство, полный файл.
5. Нажимает `Запустить`.
6. Следит за прогрессом по этапам: подготовка аудио, ASR, диаризация, склейка, экспорт.
7. После завершения открывает `Чистый Markdown`, `TXT` или `DOCX`.

Ключевое UX-требование: первый запуск не должен требовать понимания GigaSTT, pyannote, MPS, output folders и промежуточных JSON.

### Сценарий B. Проверить качество на коротком фрагменте

Цель пользователя: за 1-3 минуты понять, подходит ли модель и настройки спикеров для конкретной записи.

Основной путь:

1. Пользователь выбирает файл.
2. Переключает режим обработки на `Тестовый фрагмент`.
3. Видит готовые быстрые варианты: `первые 30 сек`, `2 минуты`, `5 минут`, а также ручные поля `старт` и `длительность`.
4. Запускает тест.
5. В результате видит короткую расшифровку, найденных спикеров и ссылки на voice samples.
6. Меняет число спикеров или backend и запускает повтор без потери предыдущего результата.

Ключевое UX-требование: тестовый фрагмент должен быть отдельным режимом, а не двумя пустыми числовыми полями, потому что это главный способ безопасно настроить длинную обработку.

### Сценарий C. Пакетно обработать папку `Inbox`

Цель пользователя: положить много записей и оставить компьютер последовательно обрабатывать их без ручного вмешательства.

Основной путь:

1. Пользователь выбирает режим `Пакет`.
2. Видит все файлы `Inbox` как будущую очередь с чекбоксами.
3. Может исключить отдельные записи, упорядочить очередь или оставить порядок по дате/имени.
4. Выбирает общие настройки и output profile.
5. Нажимает `Поставить в очередь`.
6. Видит одну активную задачу, следующие ожидающие и завершенные результаты.
7. Может открыть экспорт готовой задачи, пока остальные продолжают обрабатываться.

Ключевое UX-требование: пакетный режим должен визуально отличаться от одиночного запуска и показывать, что обработка последовательная, чтобы пользователь не ожидал параллельной нагрузки на Mac.

### Сценарий D. Назвать и исправить спикеров

Цель пользователя: превратить `Спикер 1`, `Спикер 2` в реальные имена без повторного ASR/diarization.

Основной путь:

1. Пользователь открывает завершенную задачу.
2. Видит список найденных спикеров с samples, примерными таймкодами появления и количеством реплик.
3. Прослушивает sample прямо в интерфейсе.
4. Заполняет имена, например `Андрей`, `Оля`, `Вопрос из зала`.
5. Нажимает `Применить имена`.
6. Интерфейс показывает отдельный короткий статус `перерендер экспорта`, а не полноценный повтор обработки.
7. Все ссылки на экспорт обновляются.

Ключевое UX-требование: пользователь должен понимать, что переименование спикеров быстрое и не тратит заново время на распознавание.

### Сценарий E. Диагностировать ошибку и продолжить

Цель пользователя: понять, почему задача не завершилась, и что делать дальше.

Основной путь:

1. Задача получает статус `Ошибка`.
2. Карточка ошибки показывает человекочитаемый диагноз: файл не найден, нет HF_TOKEN, нет доступа к pyannote, неверный output folder, backend недоступен, процесс завершился с кодом.
3. Рядом есть технический лог, но он не является первым и единственным объяснением.
4. Интерфейс предлагает безопасное действие: проверить токен, выбрать CPU, повторить с overwrite, открыть docs/setup-secrets.md, попробовать тестовый фрагмент.

Ключевое UX-требование: лог нужен для диагностики, но продуктовый экран должен переводить частые ошибки в понятные next steps.

## 2. Рекомендуемая информационная архитектура экранов

### Главный экран: рабочий стол обработки

Рекомендуемая структура остается одностраничной, потому что локальный инструмент выигрывает от видимого контекста: источник, очередь, результат и лог находятся рядом.

```text
Верхняя панель
  - Диктум
  - локальный адрес сервера
  - индикатор приватности: "локально, 127.0.0.1"
  - краткий статус воркера: idle / running / offline

Левая зона: Источники и запуск
  - Inbox
  - режим: один файл / тестовый фрагмент / пакет
  - пресет качества
  - раскрываемые расширенные настройки
  - запуск

Центральная зона: Очередь и прогресс
  - сводка задач
  - список задач
  - активная задача с этапами пайплайна
  - журнал активной задачи

Правая зона: Проверка и экспорт
  - summary выбранной задачи
  - preview текста
  - speaker samples и имена
  - export links
  - действия: применить имена, повторить, открыть папку
```

Текущий workflow `Inbox -> Настройки -> Очередь -> Спикеры -> Экспорт` стоит оставить, но сделать его не декоративной полосой, а навигационной картой текущего состояния: активный шаг, завершенные шаги, шаги с ошибкой.

### Режимы внутри левой зоны

#### Один файл

Фокус на выборе записи и одной кнопке запуска. Поля `старт` и `длительность` скрыты за переключателем `Полный файл / фрагмент`.

#### Тестовый фрагмент

Фокус на быстрых preset-кнопках длительности и сравнении запусков. Рекомендуется показывать историю последних тестов по выбранному файлу: backend, speaker mode, длительность, результат.

#### Пакет

Фокус на списке файлов с чекбоксами и прогнозом работы. Для каждого файла: имя, длительность, размер, предполагаемый output, статус предыдущей обработки.

### Расширенные настройки

Настройки стоит разделить на два уровня:

- Основной уровень: пресет, ASR, устройство, число спикеров.
- Расширенный уровень: точные min/max speakers, output folder, overwrite, raw speaker names, будущие параметры чанкинга и постобработки.

Это снижает шум первого запуска, но сохраняет контроль для сложных записей.

### Экран результата

В правой зоне выбранная задача должна иметь четыре вкладки:

- `Обзор`: статус, длительность, backend'ы, output folder, основные ссылки.
- `Текст`: preview Markdown/TXT с таймкодами и поиском.
- `Спикеры`: samples, имена, количество реплик, первое появление.
- `Файлы`: все артефакты, включая подробный Markdown, чистые варианты, TXT, DOCX, JSON/manifest для диагностики.

Вкладки важны, потому что текущий блок "Проверка и экспорт" смешивает ссылки, samples и действия в один список. На коротких задачах это терпимо, на длинных интервью и пакетной обработке станет плотным и менее управляемым.

## 3. Конкретные улучшения текущего UI

### 3.1. Сделать пресеты запуска главной точкой входа

Предложенные пресеты:

- `Максимальное качество`: GigaSTT/GigaAM v3, pyannote, `auto` device, полный экспорт.
- `Быстрый тест`: первые 2 минуты, рекомендуемые backend'ы, output в тестовую подпапку.
- `CPU fallback`: те же настройки, но устройство `cpu`, если MPS ведет себя нестабильно.
- `Только ASR` в будущем, если понадобится быстрый черновик без speaker labels.

Пользователь может открыть `Показать детали` и увидеть, какие CLI-параметры стоят за пресетом.

### 3.2. Добавить metadata к файлам `Inbox`

Текущий список показывает имя и размер. Для выбора записей полезнее:

- длительность;
- формат;
- дата добавления или изменения;
- статус последней обработки;
- число готовых export-файлов;
- предупреждение, если файл уже обрабатывался и overwrite выключен.

Для длинных диктофонных записей длительность важнее размера: пользователь мыслит "час двадцать", а не "68 MB".

### 3.3. Перевести числовые поля времени в понятные controls

Вместо голых `Старт, сек` и `Длительность, сек`:

- segmented control `Полный файл / Фрагмент`;
- ввод времени в формате `мм:сс` или `чч:мм:сс`;
- быстрые кнопки `0:00 + 0:30`, `0:00 + 2:00`, `0:00 + 5:00`;
- валидация "длительность фрагмента выходит за пределы файла".

Секунды можно оставить как внутренний формат, но не как основной UX.

### 3.4. Показать этапы пайплайна вместо общего `running`

Активная задача должна отображать этапы:

1. `Подготовка аудио`: ffmpeg, WAV mono 16 kHz.
2. `ASR`: выбранный backend, RTF/скорость, если известны.
3. `Диаризация`: pyannote, устройство, число/диапазон спикеров.
4. `Склейка`: reconciliation ASR words/segments со speaker turns.
5. `Экспорт`: Markdown/TXT/DOCX/manifest/samples.

Даже если backend пока не отдает структурированный progress, UI может извлекать coarse stage из строк лога или показывать "последний известный этап". Это особенно важно для 1.5-2 часовых файлов.

### 3.5. Улучшить карточки очереди

Карточка задачи должна показывать:

- имя файла;
- режим: полный файл или фрагмент;
- backend и device;
- speaker mode;
- позицию в очереди;
- elapsed time;
- completed time;
- основной action: `Открыть результат`, `Смотреть лог`, `Повторить`.

Статусы стоит локализовать: `Ожидает`, `Выполняется`, `Готово`, `Ошибка`, `Применяются имена`. Английские `queued/running/done/failed` можно оставить в API и логах, но не в основном UI.

### 3.6. Разделить пользовательский результат и технический лог

Лог сейчас занимает заметную центральную площадь. В редизайне:

- по умолчанию показывать компактный progress и последние 3-5 важных событий;
- полный лог открывать в collapsible-панели или вкладке `Журнал`;
- ошибки показывать сначала как диагноз и рекомендации, затем как raw log.

Это делает интерфейс менее похожим на shell wrapper и более похожим на рабочий инструмент.

### 3.7. Сделать speaker labeling полноценным рабочим блоком

Для каждого спикера:

- цветовая метка, стабильная в preview;
- имя;
- sample audio;
- первое появление;
- пример реплики;
- количество сегментов/примерная доля речи;
- кнопка `проиграть следующий sample`, если есть несколько samples в будущем.

После нажатия `Применить имена` нужен статус `перерендер экспорта`, disabled-state кнопки и явное сообщение `ASR и диаризация не запускаются повторно`.

### 3.8. Добавить preview текста

Минимальный preview:

- первые 20-40 строк clean transcript;
- переключатель `с таймкодами / без`;
- подсветка speaker colors;
- поиск по тексту;
- ссылка `Открыть полный Markdown`.

Это уменьшит потребность сразу открывать файлы и поможет быстро понять, получился ли результат.

### 3.9. Уточнить export-блок

Ссылки стоит сгруппировать по назначению:

- `Для чтения`: чистый Markdown, TXT.
- `Для редактуры`: Markdown с таймкодами, подробный Markdown.
- `Для документов`: DOCX, когда готов.
- `Для диагностики`: manifest JSON, raw ASR/diarization JSON.

У каждой ссылки нужен короткий secondary text: "без таймкодов", "с таймкодами", "полный debug", "для Word".

### 3.10. Добавить приватность как постоянный сигнал

Пользовательский страх для транскрибации интервью и встреч: "куда ушла запись". В верхней панели стоит постоянно показывать:

- `Локально: 127.0.0.1`;
- `Файлы не отправляются в облако` для локальных backend'ов;
- отдельное предупреждение в будущем, если выбран backend, который использует внешний API.

Это не маркетинговый блок, а рабочий trust indicator.

## 4. Состояния ошибок, длинных задач и пакетного режима

### Ошибки

Рекомендуемые error states:

| Состояние | Что видит пользователь | Действия |
| --- | --- | --- |
| `Inbox пуст` | Пустой список с путем к папке | `Обновить`, подсказка положить `.m4a/.wav/.mp3/.mp4` |
| `Файл исчез` | "Файл больше не найден в Inbox" | `Обновить Inbox`, выбрать другой файл |
| `Неверное время` | Конкретное поле подсвечено | Исправить start/duration, выбрать preset |
| `Output вне outputs/` | "Результаты должны быть внутри outputs/" | Вернуть default folder |
| `HF_TOKEN отсутствует` | "Для pyannote нужен локальный HF_TOKEN" | Открыть инструкцию setup-secrets |
| `Доступ к pyannote запрещен` | "Токен найден, но модель недоступна аккаунту" | Принять условия модели, проверить access |
| `Backend недоступен` | "ASR engine установлен как soon/недоступен" | Выбрать доступный backend |
| `MPS/GPU ошибка` | "Не удалось обработать на MPS" | Повторить на CPU |
| `Процесс упал` | Краткий код и последний релевантный лог | `Повторить`, `Смотреть полный лог` |

Ошибки должны сохраняться в карточке задачи, чтобы пользователь мог перейти к другим задачам и вернуться.

### Длинные задачи

Для файлов 1.5-2 часа интерфейс должен поддерживать "оставил и вернулся":

- elapsed time и время старта;
- текущий этап;
- последний heartbeat из лога;
- предупреждение "не закрывайте Terminal/server process";
- устойчивое состояние при refresh страницы;
- после завершения: elapsed total, где лежат результаты, какие экспорты созданы;
- если нет точного процента, показывать indeterminate progress с этапами, а не фальшивый percentage.

Для будущего чанкинга:

- показывать `chunk 3 из 18`;
- отдельно статусы ASR chunks и export assembly;
- возможность продолжить с последнего успешного intermediate-файла;
- пометка partial result, если часть chunks готова, а часть упала.

### Пакетный режим

Пакет должен иметь собственную сводку:

- `N файлов выбрано`;
- `1 выполняется`;
- `K ожидает`;
- `M готово`;
- `E ошибок`;
- общий elapsed time;
- следующий файл.

В списке задач нужны bulk filters:

- `Все`;
- `Выполняются`;
- `Ошибки`;
- `Готовые`;
- `Требуют имен спикеров`.

Для пакетного режима особенно важно действие `Открыть все готовые результаты` или хотя бы grouped export view по задачам. Пользователь не должен искать готовые Markdown-файлы среди логов и карточек.

### Offline/server states

Так как web UI живет внутри локального процесса, отдельные состояния должны быть явными:

- `Сервер доступен`: нормальный режим.
- `Сервер не отвечает`: fetch `/api/jobs` упал; показать объяснение, что Terminal/server process мог быть закрыт.
- `Очередь в памяти`: текущая реализация хранит jobs в процессе, поэтому после restart история может исчезнуть. До появления persistent job store UI должен честно показывать "история этой сессии".

## 5. Приемочные критерии для реализации редизайна

### Навигация и базовая работа

- На первом экране без прокрутки видны `Inbox`, текущий режим запуска, очередь и выбранный результат/empty state.
- Пользователь может запустить один полный файл за один основной action после выбора файла.
- Пользователь может запустить тестовый фрагмент через preset длительности без ручного ввода секунд.
- Пользователь может поставить несколько файлов из `Inbox` в последовательную очередь.
- UI не требует знания CLI-команд для основных сценариев.

### Настройки и валидация

- Основные настройки отделены от расширенных.
- ASR options показывают доступность: доступно, скоро, ошибка конфигурации.
- Speaker mode поддерживает `auto`, `точно`, `диапазон` с понятной валидацией.
- Невалидные `start/duration/speaker/output_dir` показываются рядом с полем до запуска или сразу после ответа API.
- Поля времени принимают человекочитаемый формат и корректно переводятся в секунды для API.

### Очередь и долгие задачи

- Каждая задача имеет локализованный статус.
- Активная задача показывает текущий этап пайплайна или последнее известное событие.
- Для running-задачи виден elapsed time.
- Для queued-задач видна позиция в очереди.
- Для failed-задач виден диагноз и доступен raw log.
- Refresh страницы не ломает отображение текущих in-memory задач, пока серверный процесс жив.

### Результат и экспорт

- После `done` пользователь видит export links, speaker samples и preview текста в одной правой зоне без потери выбранной задачи.
- Export links сгруппированы по назначению и имеют понятные русские названия.
- Speaker names применяются без повторного ASR/diarization, а UI явно показывает короткий статус перерендера.
- Если speaker samples или manifest отсутствуют, UI показывает нейтральное empty state, а не пустой блок.
- Для каждого результата виден output folder относительно корня проекта.

### Ошибки и восстановление

- `Inbox пуст`, `source not found`, `output_dir must stay inside outputs/`, отсутствующий/невалидный HF token и падение subprocess имеют отдельные человекочитаемые состояния.
- Ошибка не стирает форму запуска и выбранные настройки.
- Пользователь может повторить failed-задачу с теми же настройками.
- При недоступном сервере UI показывает локальную причину и следующий шаг, а не только `TypeError: Failed to fetch`.

### Визуальная и адаптивная приемка

- Desktop layout поддерживает три рабочие зоны без горизонтального скролла на ширине 1280 px.
- На ширине до 820 px зоны складываются в один поток: запуск, очередь, результат, лог.
- Кнопки и поля не меняют размер при смене статусов.
- Длинные имена файлов обрезаются с tooltip/title и не ломают сетку.
- Основные статусы различимы не только цветом, но и текстом.
- Интерфейс использует спокойную рабочую плотность: это инструмент для повторной работы, не landing page.

### Приватность и доверие

- В верхней панели всегда видно, что сервис работает локально на `127.0.0.1`.
- Для локальных backend'ов нет формулировок, которые подразумевают отправку файлов в облако.
- Если в будущем появится внешний backend или LLM API, рядом с выбором модели должен появиться явный privacy warning до запуска задачи.

## Ключевая UX-позиция

Редизайн должен сохранить текущую сильную основу: локальный рабочий стол с `Inbox`, настройками, очередью, журналом, speaker labeling и export links. Главный сдвиг не в декоративной визуальности, а в переводе интерфейса из "обертки над CLI" в "операторскую панель длинной обработки": понятные режимы, этапы пайплайна, диагностируемые ошибки, batch-контроль и быстрый путь от записи к чистому тексту.
