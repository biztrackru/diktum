# Implementation Plan

Дата: 2026-06-27.

## Ближайший фокус

Мы откладываем self-host, упаковку для публичного GitHub и внешний лендинг. Цель текущего этапа: довести локальный/private Mac-продукт до состояния, в котором обычный пользователь сможет установить и запустить его без помощи разработчика.

Исполняемый backlog с task ID, scope и acceptance criteria ведется в `.agents/product-backlog.md`. Этот документ остается стратегическим планом этапов.

## Аудит состояния на 2026-06-27

Сделано:

- рабочий local web UI с Inbox/upload/results/speaker names/exports;
- ASR chunking для длинных файлов GigaSTT;
- UX F1-F16 из Claude-прототипа в основном перенесены;
- start/stop/setup/doctor helpers существуют;
- quality diagnostics для ASR и speaker fragmentation показываются в manifest/UI.

Не закрыто полностью:

- clean/semi-clean Mac install acceptance для обычного пользователя;
- durable job queue после перезапуска сервера;
- полноценный long-file resume/progress по chunks/stages;
- надежный batch на многочасовые наборы;
- общий engine registry и реальные дополнительные local ASR profiles;
- улучшение диаризации, а не только диагностика ее проблем;
- быстрый автоматический smoke suite без приватных аудио.

## Этап 1. Надежная локальная база

Статус: готово как baseline, но product acceptance вынесен в `P0-001`.

- Зафиксировать безопасный первый git baseline.
- Убедиться, что `.env`, аудио, кеши, модели и outputs не попадают в git.
- Описать правила работы второго агента и приемки изменений.
- Сохранить текущие способы запуска/остановки через `.command` ярлыки.
- Проверить, что сервер стартует без Codex и корректно обрабатывает занятый порт.

Готово, когда:

- `git status` после коммита чистый или содержит только осознанные приватные файлы;
- README объясняет запуск/остановку;
- есть документ с правилами для AI-агентов.

## Этап 1.5. Локальная установка на Mac

Статус: частично реализовано; финальная приемка и clean Mac сценарий вынесены в `P0-001 Mac Install Acceptance`.

Цель: пользователь без технического опыта может подготовить и запустить приложение через double-click файлы.

Research-gate перед реализацией:

- изучить `QuentinFuxa/WhisperLiveKit` как референс local/self-host STT toolkit;
- решить, берем ли оттуда подход к model manager, doctor, benchmark и optional backend profiles;
- проверить, не выгоднее ли подключать WhisperLiveKit как optional Whisper backend вместо собственной Whisper-обвязки;
- явно не тащить live/WebSocket/Docker/translation фичи в локальный Mac setup, если они не нужны текущему пользовательскому пути.

Задачи:

- добавить `Настроить Voice Recognizer.command`; готово;
- добавить `app/scripts/setup_local_mac.sh`; готово;
- добавить local doctor/preflight report;
- проверить Python, `.venv`, ffmpeg/ffprobe, GigaSTT binary, модели, HF token;
- не печатать токены в лог;
- объяснять каждую проблему обычным языком;
- после успешной установки предлагать запуск сервера;
- описать ручные шаги для моделей и токенов, если автоматизация невозможна.

Готово, когда:

- пользователь может запустить setup двойным кликом;
- setup либо исправляет окружение, либо дает конкретное действие;
- после setup текущие `Запустить`/`Остановить` работают;
- путь не требует ручного использования Terminal.

## Этап 2. Импорт файлов и очередь

Статус: UI и upload в основном реализованы; надежность очереди и batch state вынесены в `P0-002` и `P0-004`.

Цель: пользователь не обязан вручную перекладывать файлы в `Inbox`, но этот путь остается.

Задачи:

- добавить загрузку одного или нескольких файлов через web UI; готово;
- сохранять uploads в локальную папку `Inbox/` или отдельную `uploads/`; готово, используется `Inbox/`;
- показывать список файлов после загрузки без перезапуска сервера; готово;
- добавить batch submit из выбранных файлов; готово;
- явно отображать очередь: waiting, running, done, failed; готово;
- не держать длинную обработку внутри одного HTTP-запроса; готово;
- сохранить очередь и историю jobs между перезапусками сервера; не готово;
- корректно восстанавливать/помечать orphan jobs после restart; не готово.

Готово, когда:

- `.m4a` можно выбрать через браузер и запустить обработку;
- несколько файлов можно поставить в очередь одним действием;
- обновление страницы не ломает уже запущенную задачу сильнее, чем текущий прототип.

## Этап 3. Длинные файлы без лимита

Статус: частично реализовано; ASR chunking готов, полноценный resume/progress вынесен в `P0-003`.

Цель: убрать практический лимит длины записи.

Задачи:

- сохранить текущий ASR chunking и покрыть его тестом; частично готово;
- добавить chunking/resume модель для diarization, если pyannote начнет падать на длинных файлах;
- записывать manifest с состоянием каждого этапа;
- переиспользовать готовые промежуточные файлы после сбоя;
- добавить понятные ошибки: не хватает памяти, токен недоступен, модель не найдена, файл поврежден.

Готово, когда:

- файл длиннее 2 часов проходит ASR без ошибки `Audio file too long`;
- после падения можно перезапустить задачу без пересчета уже готовых частей;
- в UI видно, на каком этапе задача остановилась.

## Этап 4. Выбор движков и локальных моделей

Статус: не реализовано как продуктовая возможность; см. `P0-005 Engine Registry And Model Profiles`.

Цель: пользователь выбирает качество/скорость/модель, а система объясняет последствия.

Research-gate перед реализацией:

- сравнить наш engine registry plan с backend selector WhisperLiveKit;
- проверить `wlk transcribe` и OpenAI-compatible local API как возможные adapter targets;
- отдельно оценить WhisperLiveKit Apple Silicon MLX backend на русских sample-файлах;
- не добавлять новые движки без понятной value proposition для русского batch/file workflow.

Задачи:

- выделить engine registry в отдельную конфигурацию;
- показывать доступные/недоступные движки и причину недоступности;
- описать GigaAM/GigaSTT как основной локальный русский профиль;
- добавить Whisper local profile;
- исследовать, можно ли легально и технически использовать модели/бинарники из Handy/Wisper/LM Studio;
- добавить поле "external/local" и предупреждение для внешних API.

Готово, когда:

- UI не показывает неработающий движок как обычный вариант;
- CLI и web используют один список движков;
- ошибка настройки движка содержит понятное действие для пользователя.

## Этап 5. Спикеры и качество диаризации

Статус: labeling и diagnostics частично готовы; реальное улучшение качества вынесено в `P0-006 Speaker Quality Improvement Loop`.

Цель: меньше разрывов одной фразы между спикерами и удобное назначение имен.

Задачи:

- улучшить post-processing speaker islands; не готово, есть только базовое smoothing и diagnostics;
- добавить настройку агрессивности сглаживания;
- показать overlap/low-confidence участки в диагностическом Markdown;
- сохранить speaker names в manifest/config; частично готово для manifest;
- добавить speaker memory как отдельный эксперимент, не ломая режим "только внутри файла";
- сделать samples стабильными: прослушивание не должно сбрасывать фокус и поля ввода; частично проверено, требует регрессионного smoke.

Готово, когда:

- имена применяются без повторного ASR;
- speaker samples проигрываются полностью;
- поле имени не очищается при потере фокуса/обновлении статуса;
- для каждого файла корректно работает разное число спикеров.

## Этап 6. Self-host profile

Статус: отложено до этапа перед публичной публикацией.

Цель: приватный сервер без подписки.

Задачи:

- добавить `docker-compose.yml` для web + worker + volumes;
- вынести host/port/storage/model paths в env/config;
- добавить простую локальную авторизацию для server mode;
- описать запуск на своем сервере;
- сохранить local desktop mode без Docker как основной для Mac.

Готово, когда:

- проект можно поднять через Docker Compose;
- данные сохраняются в volumes;
- случайный внешний пользователь не получает доступ к приватным файлам без настройки доступа.

## Параллельные дорожки

- Основной агент: backend, git hygiene, pipeline, tests, integration.
- Второй агент: UX/редизайн proposal, приемочные сценарии, edge cases интерфейса.
- Ревью-агент: проверка изменений перед merge/commit, поиск регрессий и приватных файлов.

Каждая дорожка должна иметь явный write scope, чтобы агенты не перетирали изменения друг друга.
